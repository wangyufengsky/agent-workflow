# 项目架构与功能解读

- **拟定大纲。** 从入口、公共接口和持久化边界识别模块。按项目实际职责命名，例如“任务状态推进”。只有具备独立功能、能落到本章具体文件的一组代码才值得单列子模块。小型模块可以直接下钻到文件。
- **解读一个功能。** 跟踪一个调用者实际能触发的动作，说明谁发起、需要什么输入、经过哪些关键判断、产生什么结果。涉及事务、并发、权限或异常时，再追到对应的写入、拒绝或清理位置。按名称复述方法往往解释不了它解决的问题。
- **建立证据。** 从实现确定行为，用测试交叉核对可观察的结果。遇到说明文档与当前实现相冲突时，写出观察到的差异和位置。用最小必要的文件与行范围支撑判断，为没有静态调用点的推断写明依据。仅引用确有解释价值的短片段，省略凭据值。
- **组织章节。** 模块级功能写在带标题与证据的正文块。子模块块按职责列出本章已分析的文件，将每个功能的解读与其证据放在一起。组成图表示归属，依赖图解释有方向的调用或数据流。保持大纲提供的章节 ID，使跨章的图节点可以跳转。
- **交易链路探索。** 在交易的主责章节把每个查实的业务入口写入 `blocks` 中的 `transaction` 块，并把它的 `diagramId` 关联到本次提交的业务流程图。提交前从档案走一遍入口、步骤、字段与证据。
- **独立复审。** 从跨模块的一条关键路径抽取入口与出口，对照两端源码验证输入、结果和错误处理是否吻合。注明抽查范围，只对实际核过的章节给出结论。
