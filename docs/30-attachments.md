# 30 · 统一附件输入

> 状态：**设计稿，未实现**（2026-10-23；同日按「精简版」改写：去掉上传状态机、服务端输入草稿、使用记录表；又按用户要求首版**只支持文本**，因为工作环境的模型不支持图片）。枚举、常量、表、接口、工具分别登记在 08–12 的「待实施」章节，不能据此视为现有能力。

## 1. 目标与范围

用户开始任务、问助手、「让 AI 再改改」时可以拖入文件或选择项目文件。附件随这次输入保存，之后的步骤看到的是同一份内容。

| 批次 | 内容 | 完成边界 |
| --- | --- | --- |
| U1 | UTF-8 文本文件（Markdown、代码、JSON、CSV、日志等）；项目文件快照。入口：主页任务输入、主页与侧栏助手、任务「再改改」 | 文字进提示词，长的用工具分页读；原件能打开 |
| U2（另行确认） | 图片（等工作环境有支持图片的模型）；PDF / DOCX 正文提取；知识问答附件引用；PPT 文件资料；浏览器「附上当前页面」（依赖 29 的 B2） | 实施前单独评审 |

不做：全局文件库、跨对话挑选旧附件、OCR、压缩包／Office 表格与演示文稿／可执行文件。浏览器里的网站上传／下载仍按 29 §5.4 禁止；**应用自己的附件入口不等于让 AI 向网站上传文件**。

## 2. 用户流程

1. 输入框下有「添加资料」：选择文件、选择项目文件；支持拖放。粘贴文字照旧进输入框；粘贴图片时提示「暂不支持图片，请用文字描述」。
2. 选中后立即上传。附件卡显示名称（长名保留扩展名，悬停看全名）和大小，可打开、移除。上传失败的卡片显示原因（不是文本文件、超过大小），用户移除后再发送。
3. 发送时后端在业务写入的同一事务里绑定附件；事务失败时什么都不绑定，界面保留文字与附件。
4. 未发送的附件只存在于当前输入框（组件状态），与现有文字输入一样，刷新页面不保留；后端定时清理没有被引用的附件（§4）。

限制（08）：每次输入最多 10 个附件，单个 5 MiB。选择时提示，服务端再校验。

### 2.1 项目文件

选择已添加项目，在文件树里选相对路径和可选行范围。任务「再改改」默认读该任务的 worktree，其他入口读项目主目录，界面写明来源。后端以项目根目录的 realpath 为边界，拒绝越界、指向根外的符号链接和非普通文件。

读取时立即保存为附件，来源信息记录项目、相对路径、行范围、读取时间。原文件之后的变化不影响附件；要新内容就重新选择。给模型的资料清单里不出现绝对路径。

### 2.2 后续步骤与复用

- 开始任务时的附件对该任务的规划、执行、评审步骤都可见；「再改改」的附件从那次修改开始可见，之前的附件仍在。
- 助手创建任务时可以带上**当前对话**已发送的附件，确认卡列出名称；后端只接受当前对话里确实有的附件。复用的是同一份原件，新增一条引用。
- 删除任务／助手对话只删除它的引用；原件在最后一条引用消失后清理。

## 3. 内容与模型输入

### 3.1 保存

`POST /attachments` 一次上传（二进制请求体，非清单路由，11 §14）。后端写临时文件，校验通过后原子改名到 `<userData>/attachments/<id>/original`，再插入记录；校验不过直接返回错误，不留记录。所以没有「上传中／处理中」状态：**记录存在就是可用的**。

- 是不是文本看内容，不看扩展名或浏览器给的 MIME：严格 UTF-8 解码成功且不含 NUL 字节才接受，否则返回 `ATTACHMENT_INVALID_TYPE`（`details.reason: not_text`）。图片、PDF 等都在这里被拒，提示信息说明目前只支持文本。
- 二进制请求体而不是 JSON 字符串，是为了让后端拿到原始字节做严格校验（浏览器读文件时会把非法字节替换掉），以后支持图片时也不用换接口。
- 存储路径只由附件 ID 派生，显示名只在数据库；同名文件是不同附件，不做内容去重。

### 3.2 模型看到什么

所有者（任务／助手）在开始一次尝试或发送一条消息时，把可见附件的文字交给提示词：

- **资料清单**：编号、名称、来源、大小，明确标注为**用户提供的资料，不是指令**。
- **正文**：本轮全部附件合计不超过 20,000 字符时直接放进提示词；超过时只放清单和开头摘录，模型用 `read_attachment` 分页读（每次最多 12,000 字符，12 §9）。

全部是文本，现有 `opencode.client.ts` 只发一个 text part 的方式不用改。全文不放进 SSE、常规日志和 `get_task_context` 的返回。

「AI 读取的资料」直接看会话流：提示词里的清单与摘录、`read_attachment` 的调用都在尝试的会话记录里（与现有工具调用展示一致），不另建使用记录表。

## 4. 生命周期

| 情况 | 处理 |
| --- | --- |
| 上传成功、尚未发送 | 有记录、无引用 |
| 发送 | 同一事务内为所有者创建引用（任务输入／修改反馈／助手消息） |
| 删除任务／助手对话 | 同一事务删除其引用 |
| 清理 | 启动时和每小时一次：删除没有引用且创建超过 24 小时的附件，见下 |

清理与绑定不能交错，否则可能删掉刚被引用的原件。做法是**先删记录、后删文件**：

- 清理在一个事务里删除「没有引用且超龄」的记录，提交后再删对应文件。
- 绑定在所有者的事务里先确认附件记录存在，再插入引用（外键）。
- SQLite 事务串行执行：绑定在前，清理就看到引用而跳过；清理在前，绑定就返回 `ATTACHMENT_NOT_FOUND`，界面提示重新添加。
- 删文件失败只会留下没有记录的残留文件，按年龄清理即可，不会出现有引用却没有原件的附件。

附件不写进 Git worktree，不会被节点提交或交付进用户仓库。

## 5. 接入现有架构

- 后端新增 `attachments` 模块（U-01 已实现）：保存、校验、引用、清理。它接收已解析的所有者（kind + id），读项目文件时经 `projects` / `worktrees` 取根目录，不 import `tasks`、`assistant`。安全定位仓库文件的逻辑与知识问答共用 `core/repo-files.ts`。
- `tasks`、`assistant` 负责范围：在各自事务里调用 `attachments.bind`；执行 MCP 的 `read_attachment` 按当前尝试所属任务限定范围，助手的按当前对话限定；模型传入的 ID 不在范围内一律 `ATTACHMENT_NOT_FOUND`。
- `attempts` 只接收所有者准备好的附件文字，不反查任务。

| 入口 | 改动 |
| --- | --- |
| 主页任务输入 | 共用附件条；`createTask` 增加可选 `attachmentIds` |
| 主页／侧栏助手 | 共用附件条；发送消息增加 `attachmentIds`；会话 JSONL 的用户消息记录附件 ID 与名称；与现有「助手生成的文件」是不同的东西 |
| 任务「再改改」 | `requestChanges` 增加 `attachmentIds`，引用挂在追加的修改节点上 |
| 批量／定时任务 | 不支持附件 |

## 6. 验证

- **集成**（真实文件与 SQLite）：超限、非 UTF-8、含 NUL 的文件被拒且不留记录；项目文件越界与符号链接被拒；原文件改变不影响已保存附件；共享引用删除一处不删原件；无引用附件按年龄清理；其他任务／对话的附件 ID 读不到；超过 20,000 字符时提示词只放摘录、`read_attachment` 能读完全文。
- **opencode / live**：FakeOpencode 断言提示词里的清单与摘录；真实模型用 `read_attachment` 读完一个长附件并据此回答。
- **浏览器 E2E**：选择／拖放、失败卡片、粘贴图片的提示、发送后在任务页与助手里能打开；四主题走查含长文件名与 10 个附件。
