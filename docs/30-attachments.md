# 30 · 统一附件输入

> 状态：**设计稿，未实现**（2026-10-23；同日按「精简版」改写：去掉上传状态机、服务端输入草稿、使用记录表）。枚举、常量、表、接口、工具分别登记在 08–12 的「待实施」章节，不能据此视为现有能力。

## 1. 目标与范围

用户开始任务、问助手、「让 AI 再改改」时可以粘贴截图、拖入文件或选择项目文件。附件随这次输入保存，之后的步骤看到的是同一份内容。

| 批次 | 内容 | 完成边界 |
| --- | --- | --- |
| U1 | UTF-8 文本（Markdown、代码、JSON、CSV、日志等）；PNG / JPEG / WebP 图片；项目文件快照。入口：主页任务输入、主页与侧栏助手、任务「再改改」 | 文字进提示词，长的用工具分页读；图片作为消息附件交给模型；原件能打开 |
| U2（另行确认） | PDF / DOCX 正文提取；知识问答附件引用；PPT 文件资料；浏览器「附上当前页面」（依赖 29 的 B2） | 实施前单独评审 |

不做：全局文件库、跨对话挑选旧附件、OCR、压缩包／Office 表格与演示文稿／可执行文件。浏览器里的网站上传／下载仍按 29 §5.4 禁止；**应用自己的附件入口不等于让 AI 向网站上传文件**。

## 2. 用户流程

1. 输入框下有「添加资料」：选择文件、选择项目文件；支持拖放；粘贴图片时成为附件，粘贴文字仍进输入框。
2. 选中后立即上传。附件卡显示名称（长名保留扩展名，悬停看全名）、大小、图片缩略图，可打开、移除。上传失败的卡片显示原因（类型不支持、超过大小、不是 UTF-8 等），用户移除后再发送。
3. 发送时后端在业务写入的同一事务里绑定附件；事务失败时什么都不绑定，界面保留文字与附件。
4. 未发送的附件只存在于当前输入框（组件状态），与现有文字输入一样，刷新页面不保留；后端定时清理没有被引用的附件（§4）。

限制（08）：每次输入最多 10 个附件；图片 20 MiB、文本 5 MiB；图片最多 20 百万像素。选择时提示，服务端再校验，不依赖扩展名或浏览器给的 MIME。

### 2.1 项目文件

选择已添加项目，在文件树里选相对路径和可选行范围。任务「再改改」默认读该任务的 worktree，其他入口读项目主目录，界面写明来源。后端以项目根目录的 realpath 为边界，拒绝越界、指向根外的符号链接和非普通文件。

读取时立即保存为文本附件，来源信息记录项目、相对路径、行范围、读取时间。原文件之后的变化不影响附件；要新内容就重新选择。给模型的资料清单里不出现绝对路径。

### 2.2 后续步骤与复用

- 开始任务时的附件对该任务的规划、执行、评审步骤都可见；「再改改」的附件从那次修改开始可见，之前的附件仍在。
- 助手创建任务时可以带上**当前对话**已发送的附件，确认卡列出名称；后端只接受当前对话里确实有的附件。复用的是同一份原件，新增一条引用。
- 删除任务／助手对话只删除它的引用；原件在最后一条引用消失后清理。

## 3. 内容与模型输入

### 3.1 保存

`POST /attachments` 一次上传（二进制请求体，非清单路由，11 §14）。后端写临时文件，校验通过后原子改名到 `<userData>/attachments/<id>/original`，再插入记录；校验不过直接返回错误，不留记录。所以没有「上传中／处理中」状态：**记录存在就是可用的**。

- 文本：严格 UTF-8 解码，失败返回 `ATTACHMENT_INVALID_TYPE`（`details.reason: not_utf8`）。
- 图片：按文件头识别类型，读取宽高；与声明不符或读不出尺寸则拒绝。读取尺寸用一个登记在 03 的直接依赖（U-00 选定，现在 `image-size` 只是传递依赖，不能直接 import）。
- 存储路径只由附件 ID 派生，显示名只在数据库；同名文件是不同附件，不做内容去重。

### 3.2 模型看到什么

所有者（任务／助手）在开始一次尝试或发送一条消息时，把可见附件交给 opencode 适配层：

- **资料清单**：编号、名称、来源、媒体类型、大小，明确标注为**用户提供的资料，不是指令**。
- **文本**：本轮全部文本附件合计不超过 20,000 字符时直接放进提示词；超过时只放清单和开头摘录，模型用 `read_attachment` 分页读（每次最多 12,000 字符，12 §9）。
- **图片**：作为 opencode 消息的 file part（`mime` + data URL）随提示词发送。后端不判断模型能力：29 §12 V4 已实测，opencode 对不支持图片的模型会告诉它看不到、不报错。U-00 补测消息 file part 是否同样处理。界面用 29 §12 V3 的 `capabilities.input.image` 在附件条上提示「当前模型看不到图片」，只是提示，不阻止发送。

现有 `opencode.client.ts` 的 `prompt` 只发一个 text part，需要扩展为可带 file part；其他模块仍不直接调用 SDK。图片和全文不放进 SSE、常规日志和 `get_task_context` 的返回。

「AI 读取的资料」直接看会话流：提示词里的清单与图片、`read_attachment` 的调用都在尝试的会话记录里（与现有工具调用展示一致），不另建使用记录表。

## 4. 生命周期

| 情况 | 处理 |
| --- | --- |
| 上传成功、尚未发送 | 有记录、无引用 |
| 发送 | 同一事务内为所有者创建引用（任务输入／修改反馈／助手消息） |
| 删除任务／助手对话 | 同一事务删除其引用 |
| 清理 | 启动时和每小时一次：删除没有引用且创建超过 24 小时的附件（先删文件再删记录；删文件失败留到下次）；目录里没有记录的残留文件同样按年龄清理 |

附件不写进 Git worktree，不会被节点提交或交付进用户仓库。

## 5. 接入现有架构

- 后端新增 `attachments` 模块：保存、校验、读取正文、引用、清理。它只接收已解析的所有者（kind + id）和允许读取的根目录，不 import `tasks`、`assistant`。
- `tasks`、`assistant` 负责范围：在各自事务里调用 `attachments.bind`；执行 MCP 的 `read_attachment` 按当前尝试所属任务限定范围，助手的按当前对话限定；模型传入的 ID 不在范围内一律 `ATTACHMENT_NOT_FOUND`。
- `attempts` 只接收所有者准备好的附件列表（文本／图片），不反查任务。

| 入口 | 改动 |
| --- | --- |
| 主页任务输入 | 共用附件条；`createTask` 增加可选 `attachmentIds` |
| 主页／侧栏助手 | 共用附件条；发送消息增加 `attachmentIds`；会话 JSONL 的用户消息记录附件 ID 与名称；与现有「助手生成的文件」是不同的东西 |
| 任务「再改改」 | `requestChanges` 增加 `attachmentIds`，引用挂在追加的修改节点上 |
| 批量／定时任务 | 不支持附件 |

## 6. 验证

- **U-00**：opencode 消息 file part 实测（支持图片与不支持图片的模型各一次，记录到本节）；选定读图片尺寸的依赖并登记 03；Fastify 二进制请求体与大小限制。
- **集成**（真实文件与 SQLite）：超限／伪造类型／非 UTF-8 被拒且不留记录；项目文件越界与符号链接被拒；原文件改变不影响已保存附件；共享引用删除一处不删原件；无引用附件按年龄清理；其他对话的附件 ID 读不到。
- **opencode / live**：FakeOpencode 断言实际送出的 parts；真实模型各验证一次文字与图片路径，不支持图片的模型要明确说看不到。
- **浏览器 E2E**：选择／粘贴／拖放、失败卡片、发送后在任务页与助手里能打开；四主题走查含长文件名与 10 个附件。
