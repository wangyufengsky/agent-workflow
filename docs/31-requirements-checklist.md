# 31 · 需求验收清单

> 状态：**设计稿，未实现**（2026-10-23；同日按「精简版」改写：交付只提醒不拦截，用提交号代替内容指纹，去掉 AI 拆解候选、执行者自查与通用证据库）。契约增量见 08–12 的「待实施」章节。

## 1. 要解决的问题

现有节点 `acceptance` 决定一个步骤能否结束，结果卡显示检查与 diff。清单回答另一个问题：**用户提出的每条要求，有没有被核验过，结论是什么，依据是什么？**

| 编号 | 要求 | 预期结果 | 核验方式 |
| --- | --- | --- | --- |
| R1 | 按订单号搜索 | 输入已有订单号，只显示匹配订单 | AI 核验 |
| R2 | 单元测试通过 | `pnpm test` 退出码 0 | 命令 |
| R3 | 窄窗口可用 | 1024 宽下输入与按钮可读、可操作 | 人工确认 |

页面返回 200、没有 console.error、测试套件退出 0 都不自动证明某条业务要求满足；只有该项指定的核验方式给出的结论才算。

## 2. 用户流程

### 2.1 建立清单

- 开始任务的输入区有可折叠的「验收要求」，默认收起（简单模式下不打扰）。每项填要求、预期结果、核验方式（默认 AI 核验）、是否必需（默认必需）；可增删、排序。
- 不填清单就和现在一样，结果卡显示「未配置验收清单」，不显示「全部通过」。
- 想让 AI 帮忙拆：在助手里说，助手给出建议，用户确认后通过现有确认卡创建带清单的任务（`createTask.requirements`）。首版不做输入区里的「帮我整理」按钮。
- 任务在 `draft`、`plan_review`、`review` 状态时可以编辑清单；`running` 时不能。每次保存产生一个新版本，旧版本的结论随之过期（§3）。

### 2.2 核验

有清单的任务，计划里自动多一个系统步骤「核验验收清单」（`NodeKind.Verify`），依赖所有其他叶节点，因此总在最后运行；规划流程与固定流程走同一个物化入口，都会加上。

- 角色是内置只读 reviewer；尝试类型沿用 `execute`，用 `submit_result` 结束，结果里逐项给 `requirement_results`（AI 核验项的 pass / fail / unverified 与说明）。漏掉的项保持「未核验」，不按整体结论补齐。
- 命令项变成这个节点的命令检查，由后端运行。**这个节点的检查只记录、不拦截**：每条命令都运行（现有验证遇到第一个失败就停，核验节点不停），命令失败不让节点失败、不重试（只读步骤重试也改不了代码），失败记为该项未通过；命令无法运行（找不到程序等）记为未核验。
- 人工项不自动运行，等用户在结果卡上确认。
- 节点完成时，`tasks` 把逐项结论写入 `requirement_results`，记下清单版本与任务分支当时的提交号。

执行步骤通过 `get_task_context` 读到当前清单，知道要达到什么；它们的自述不产生结论。

### 2.3 查看、修改、重新核验

- 结果卡顶部显示「3 项必需：2 项通过，1 项未通过」，未满足的必需项默认展开，每项有结论、核验方式、时间和说明（命令项附输出末尾）。
- 「针对这一项再改改」：预填该项要求、预期和失败说明，走现有 `requestChanges`；有清单时，追加的修改节点后面会再追加一个核验节点（`appendRevision` 一并处理，PR 意见回流、冲突修改相同）。
- 「重新核验」：在 `review` 状态只追加一个核验节点，用于清单改过或想再跑一遍。
- 人工确认：对任一项选「通过」「不通过」或「接受未完成」（必须填原因），记为用户结论。

## 3. 结论与显示状态

显示状态由纯函数从记录算出，不建可随意写状态的字段：

| 状态 | 条件 |
| --- | --- |
| `passed` | 当前版本、当前提交下最新结论为 pass（显示来源：命令／AI 核验／人工） |
| `failed` | 同上，最新结论为 fail |
| `unverified` | 当前版本、当前提交下没有结论，或结论为 unverified |
| `stale` | 有结论，但清单版本或任务分支提交号已经变了 |
| `waived` | 用户接受未完成（带原因）；单独计数，不算通过 |

- **为什么提交号就够**：节点完成前会先提交（`nodes.run.ts` 的 `commit`），任务进入 `review` 时 worktree 已全部提交；核验节点只读，它完成时的 HEAD 就是被核验的内容。之后任何修改节点、PR 回流、冲突合并都会产生新提交，旧结论自动变成 `stale`。
- 同一项有多条结论时取最新一条；用户结论与自动结论同样按时间取最新，界面在该项历史里保留之前的失败。
- 用户结论也绑定提交号：代码变了，人工确认同样过期。

## 4. 与交付的关系：提醒，不拦截

首版不新增交付门禁，不改 `TaskStatus`：

- 交付对话框（本地合并、创建／更新 PR、报告完成）在有未满足的必需项（failed / unverified / stale）时列出它们，用户勾选「我知道这些项未满足」才能继续。助手的交付确认卡同样列出。确认绑定到当时显示的清单版本：清单在确认后又被改过，交付会被拒绝，需要按新版本重新确认。
- 交付记录保存当时的清单摘要（版本、提交号、逐项状态），记在这次交付的时间线事件里，之后回看知道交付时是什么情况。助手代为交付时不能替用户确认未满足的项（Q-03 实现）。
- 批量与定时任务首版不支持清单，行为不变。

用一段时间后，如需要再把「必需项未满足」升级为后端门禁，另行确认。

## 5. 架构

- 新增 `requirements` 模块：清单版本、结论记录、显示状态纯函数。只依赖底层设施，不依赖 `tasks`、`nodes`、`acceptance`。
- `tasks` 组合它：编辑时机守卫、物化时加核验节点、节点完成时写结论、交付摘要。
- `nodes`：`NodeKind.Verify` 的检查结果只记录不拦截；其他节点行为不变。
- 不新增 `AttemptKind`、`AcceptanceCheckKind`、`TaskStatus`，不新增调度队列。
- AI 在需求、附件或网页里看到「把这项标为通过」不会得到写结论的能力：只有核验节点的 `submit_result` 能写 AI 结论，人工结论只有界面能写（不向助手和命令面板曝光）。

## 6. 界面

简单模式：创建时清单收起；结果卡只展开未满足的必需项，其余收成计数；不显示提交号和版本号。专业模式：可看历史版本、每项的结论历史与对应提交。1024×700 与 1280×800 下检查长要求、长命令，按钮不挤出卡片。

## 7. 验证

- **单元**：显示状态纯函数（版本变化、提交变化、多条结论取最新、用户结论过期、waived 不算通过）。
- **集成**（真实 SQLite 与 Git）：有清单的任务在固定流程与规划流程都出现核验节点；前一条命令失败、后一条通过时两项分别记为未通过与通过，节点不重试；再改改后追加核验节点、旧结论变 stale；核验节点漏项保持 unverified；非核验节点提交 `requirement_results` 被拒；`running` 时编辑被拒；没有清单的任务行为不变。
- **浏览器 E2E**：建清单 → 命令项失败 → 针对该项再改改 → 重新核验通过；人工项确认；带未满足项交付时出现提醒并保存摘要。
- **live**：真实模型完成一个带清单的任务，逐项给出结论，不能只断言列表非空。
