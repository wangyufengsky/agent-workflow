# AI 助手能力与缺陷评审

评审日期：2026-10-24（Asia/Shanghai）。基线：`feat/U-attachments@eeb1563`，评审开始时工作区干净。

后续状态：F1–F4 已修复并完成回归与全量验证，见[修复记录](assistant-consistency-fixes-2026-10-24.md)。下文保留修复前的评审事实；其余能力扩展未实施。

本报告针对当前项目的应用助手，以及它连接任务、知识问答、PPT、附件与桌宠的方式。依据当前源码、操作契约和隔离集成复现；没有运行本轮真实模型、浏览器或 Electron 验收，也不据此给出模型准确率或任务成功率评分。

## 1. 判断

当前助手具备较广的应用操作能力，适合“查询现状 → 发起操作 → 用户确认 → 打开结果”的交互。持续跟进长任务、跨重启恢复、丰富资料输入和屏幕理解仍有明显缺口。

最先应处理的是操作结果的一致性：用户点确认后，界面、数据库和模型必须对“发生了什么”保持一致。本轮复现了 4 个破坏这种一致性的问题。

## 3. 已复现的缺陷

### F1 · P1：无返回值操作成功后，确认结果损坏，整个确认列表读取失败

复现：在隔离项目中，通过助手请求 `projects_delete` 并确认。项目已删除（查询 404），但确认请求返回 500，再查询该对话的确认卡列表也返回 500。

根因：`runOperation` 产生 `{ ok: true, output: undefined }`；JSON 序列化后只剩 `{ "ok": true }`；重新读取时，Zod 4 的必填 `output: z.unknown()` 拒绝缺失字段。后续发布结果和回传模型都被阻断。这不是删除失败，而是成功的业务动作被错误报告。

当前有 15 个助手可调用操作返回 void，包括项目/数据库/流程/角色/定时/知识/PPT 删除，以及部分 Git 操作；走人工确认路径时共用此缺陷。write 操作已设为总是允许而直接执行时走另一条路径。

定位：
- `packages/shared/src/contracts/api/assistant.ts:82`
- `packages/server/src/modules/assistant/assistant.repo.ts:27`、`:100`
- `packages/server/src/modules/assistant/assistant.confirmations.ts:128`

建议：为无返回值成功定义可持久化的明确表示；同步运行时结果、JSON 存储与 schema，并兼容已经写入的缺失 output 记录。回归应覆盖真实 void 操作成功后的确认接口、确认列表及模型回传。

### F2 · P2：同一新对话并发发送会创建两个底层会话

复现：让第一条消息的外部建会话请求暂时挂起，再向同一对话发送第二条；放行后两个请求均返回 200，创建了两个 opencode 会话。预期应只创建一个，另一条拒绝为 busy 或按明确策略排队。

根因：`send` 先检查 busy，但直到等待 `sessionOf` 完成后才在 `prompt` 中设为 busy。创建会话的异步窗口内没有占用或串行化。数据库最终只保留后一个会话 ID，之前的上下文分散在另一个会话，工具归属也可能失效。主窗口与桌宠共享同一对话使这个场景具有现实触发入口。

定位：`packages/server/src/modules/assistant/assistant.service.ts:168`、`:187`、`:331`。

建议：在首次异步操作前按对话取得执行权；统一用户发送、系统回传和创建会话的串行化规则，并在失败时释放。

### F3 · P2：已经执行的确认结果在重启后丢失回传

复现：助手请求修改项目名称 → 模型运行时断开 → 用户确认且名称修改成功 → 重启后端并保留原 SQLite 与 opencode 会话 → 用户发送“继续”。模型只收到“继续”，没有收到已经完成的修改结果；确认卡记录仍在。

根因：待发送结果只保存在 `Live.outbox: string[]` 中，重启会清空。已有持久化确认结果没有投递状态与恢复扫描。正常聊天历史仍可以保留，这个缺陷特指尚未送达模型的应用结果。

定位：`packages/server/src/modules/assistant/assistant.service.ts:67`、`:112`、`:208`、`:384`。

建议：保存待投递消息与投递状态，在启动或会话恢复时重放；通过消息标识和业务幂等规则避免恢复时重复执行已经完成的操作。确认已开始但尚无结果的中断状态也需要明确的恢复处理。

### F4 · P2：旧页面对象消失，会把成功操作报告成失败

复现：在项目详情页发起“切换专业模式”的确认；通过另一入口删除该项目；再确认切换。设置修改成功且卡片结果 `ok: true`，但确认接口返回 404，模型没有收到结果。

根因：自动回传沿用最后一次用户消息的页面引用，`flush` 调用 `system(c, state.page)` 时重新读取已删除的项目，抛出 `PROJECT_NOT_FOUND`。操作本身的成败与补充页面上下文被绑定在同一失败路径。

定位：`packages/server/src/modules/assistant/assistant.service.ts:215`、`assistant.context.ts:113`、`assistant.confirmations.ts:132`。

建议：区分用户新消息的页面校验与系统结果回传。系统消息明确记录“原页面对象已删除”，可靠送达已完成操作的结果；不要让旧页面引用把成功操作转换成 HTTP 失败。

## 4. 产品能力缺口与实现风险

这些内容与上面的可复现缺陷分开处理，其中一些是当前明确的产品范围。

| 缺口 | 当前证据与用户影响 | 建议 |
| --- | --- | --- |
| 长任务缺少自动汇报和后续行动 | `assistant/index.ts:64` 的异步回传只注册知识问答。普通任务、PPT 和 Git 审查会更新卡片/通知，但未接入统一的“结束后唤醒原助手、读取结果、继续处理”机制 | 保存发起对话与任务关系，提供结束事件、结果摘要和后续步骤；继续保留交付确认 |
| 上下文感知较浅 | `assistant.context.ts` 主要提供页面类型、对象 ID、标题、状态等元数据；不包含当前报错正文、选中文本、屏幕画面或未提交表单 | 增加用户主动附加的选区、报错、文件及页面快照，并展示实际发送了哪些上下文 |
| 附件只有文本 | 上传按严格 UTF-8 且不含 NUL 校验；没有图片、扫描件、PDF、DOCX、XLSX 的解析链路 | 根据真实使用场景优先支持截图与 PDF，再扩展办公文档 |
| 助手没有内置浏览器操作能力 | 预览操作明确 `assistant: false`；助手拒绝执行 MCP，现有浏览器工具属于执行 MCP；文档 B3 才接助手 | 复用现有浏览器边界接入助手，提供显式页面读取和受控操作 |
| 缺少产品级跨会话记忆 | 对话历史和 opencode 会话可复用；当前助手模块没有偏好/事实记忆、检索、用户查看编辑删除记忆的闭环 | 先明确哪些记忆可保存，再实现可追溯、可撤销的记忆管理 |
| 助手用量与运行约束不足 | `insights.repo.ts:44` 的聚合查询仅统计任务与知识研究；普通助手/碎碎念没有纳入该用量汇总。主助手未配置自己的回合时间/工具调用上限，碎碎念单独有超时 | 按会话展示 token、耗时和调用数；定义主助手超时、中断及恢复策略 |
| 工具选择负担需要评测 | 工具列表只按简单/专业模式过滤；专业模式提供 140 个应用工具。尚无证据证明已经导致模型选错或变慢 | 用真实多轮任务测工具选择成功率、时延与 token，再决定是否按意图分组或检索工具 |
| 原生文件访问的会话隔离偏宽 | 所有会话的原生工作目录均为 `<dataDir>/assistant`；该目录包含所有会话的 files 与 transcripts；agent 允许 edit，只禁止 external_directory。MCP 的本对话校验未形成同样的原生工具边界 | 使用每对话工作目录，且把应用维护的聊天记录置于模型不可编辑位置；本轮仅确认配置与路径关系，未跑真实 opencode 越界用例 |
| 删除聊天没有清理底层会话 | `assistant.service.ts:305` 清理应用记录和文件，但没有调用已有的 `opencode.deleteSession`；碎碎念结束则会调用 | 明确聊天删除的数据范围；若按彻底删除设计，应同步删除底层会话。本轮为源码发现，未验证真实 opencode 存储残留 |

## 5. 验证结果与后续顺序

本轮实际运行：

- 现有助手、附件、前端助手纯逻辑及桌宠通知相关测试：**11 个文件、62 项全部通过**。
- 隔离复现：**4 个行为断言均失败，分别确认 F1–F4**。真实 SQLite、文件系统与临时 Git 仓库，模型使用 FakeOpencode；并发场景只延迟外部建会话调用。
- 最初的复现脚本有调度同步与结果读取问题，修正探针后才采用最终这轮结果；未修改产品实现或原有测试断言。
- 没有运行本轮真实模型、浏览器或 Electron 测试。现有 live 用例覆盖日期+项目查询、长附件末尾读取，以及桌宠基础消息/碎碎念；不足以证明复杂多轮任务的稳定性。

复现脚本和最终输出见 [证据目录](assistant-review-evidence-2026-10-24/)。脚本保存为 `.ts.txt`，不会加入日常测试发现范围。复跑时复制到 `packages/server/test/assistant-review-probes.int.test.ts`，运行 `pnpm exec vitest run --project int packages/server/test/assistant-review-probes.int.test.ts`，结束后删除该临时副本。

建议顺序：

1. **先修结果一致性**：F1、F2、F3、F4；同时明确会话文件隔离和聊天删除范围。
2. **补齐长任务闭环**：任务/PPT/审查完成后回到原对话，能总结结果和推进已授权后续步骤。
3. **补真实多轮评测**：从自然语言创建任务、确认、执行、报错、修正到交付；覆盖重启、多窗口、附件和取消，记录成功率与人工介入次数。
4. **再扩展感知与记忆**：截图/PDF、浏览器、可控长期记忆；用量与超时约束同步建设。
