## 2. 任务验收与恢复

### UX-01 修改条件后重新核验

**当前行为。** 步骤检查命令导致任务失败时，`tasks.updateCheckCommand` 可以更新命令并用已提交结果重新检查。任务级验收清单的编辑和重新核验分属两个操作，`tasks.reverifyRequirements` 限制在待合并状态。

**界面与服务。**

- 在失败面板和对应的「需要你处理」条目提供「修改条件并重新核验」。对话框显示失败步骤、最近一次结论、原条件及可编辑字段。覆盖检查命令、任务验收清单的要求与预期、核验方式及其命令。预览服务启动失败时沿用项目预览设置入口。默认本任务生效，修改检查命令时可显式选择同时更新项目默认值。
- 服务端按失败阶段、失败步骤、工作区状态和已提交结果判断资格。准备、规划或执行未提交结果时，界面直接说明适用的继续或重跑入口。发现代码本身的问题时保留「带上说明重试」和待合并状态的「再改改」。
- 沿用 `tasks.checks.ts`、`tasks.changes.ts`、`tasks.verify.ts` 和节点核验入口。步骤检查重新使用已提交结果，按依赖顺序运行改过的检查及其后尚需运行的检查。清单保存新版本后按新版本调度核验，沿用旧结论过期规则。待合并时追加核验节点。任务因核验节点失败而停下且已有可核验结果时，从该节点恢复，待通过后再推进下游。需要模型的清单项走现有只读核验步骤。
- 在同一事务中校验预期的任务状态、结果提交和清单版本，持久化条件变化并登记新的核验。提交后开始执行。连续点击、并发修改或核验时提交变化时返回可理解的状态提示。时间线记录核验前后的条件、提交和结论，结果卡指向本次证据。
- 将可核验范围和写操作风险登记到操作清单。`aw-task-diagnosis` 在建议动作前先查失败证据，说明会改哪项及影响范围，再通过已有确认卡提交。人工验收结论由用户在界面提交。

**验收。** 真实 Git 与 FakeOpencode 测试覆盖修改命令后核验成功，原执行步骤的尝试数与产出内容保持一致。已经提交的结果保留原提交，之前尚未通过检查的结果在通过后按原规则提交。覆盖待合并修改清单后重验、失败且有有效结果的清单核验、无有效结果时拒绝、重验仍失败、重复提交、工作区不可用和旧清单结论可追溯。浏览器走通「看输出 → 改条件 → 核验 → 回到待合并」。

### UX-02 待合并任务的流程图前置

**界面。** 将 `TaskStatus.Review` 的流程图作为任务详情正文第一块，默认展开，后接验收结果、改动详情和交付操作。沿用 `StepsView` 与现有步骤定位，给图下内容保留「查看验收结果」跳转。用户可以手动折叠流程图。

**验收。** 浏览器分别验证执行中转入待合并、直接访问已有待合并任务和刷新后的首屏，流程图均先于结果卡且默认展开。键盘可折叠和展开，点击节点仍能打开详情。在简单与专业模式、1024×700 和 1280×800 窗口检查长流程和交付操作的可达性。

### UX-03 结果卡与验收证据直达

**界面。** 流程图下的结果卡先显示改动概述和需要用户判断的验收项。把不通过、尚未核验、已跳过或人工接受的项带上准确状态，链接到对应步骤的命令输出、浏览器截图、AI 结论或改动位置。已有「查看步骤」和「重新核验」入口优先复用。

**数据。** 按当次核验的步骤、尝试、清单版本和提交定位证据。需要读结果时延迟加载对应输出。`tasks.diff.ts` 的运行中视图沿用 worktree。本地合并在仓库锁内取得目标分支交付前后的提交，PR / MR 交付记录对比基线和本次推送的 head。交付成功后可用这些提交复用 Git diff 浏览器。旧记录有可信提交时读取对应 Git 证据，证据被清理或区间不可恢复时展示结果摘要和明确的不可用原因。

**验收。** 浏览器从未通过项打开原始命令输出、从页面体检项打开对应截图。集成测试验证 squash、merge、rebase 和 PR 推送后的 diff 只包含对应交付的改动。任务工作区清理且目标分支继续提交后，历史 diff 的范围仍与原交付一致。覆盖旧记录和已经被清理的证据。

## 3. 项目对话与对话续接

### UX-04 助手会话绑定项目

**界面。** 主页「问助手」和侧栏助手的新对话输入区提供项目选择器，默认「通用对话」。从项目详情页新建时预选当前项目，可在发送第一条消息前调整。开始对话后一直显示其项目，用户可以从项目选择器开启另一个项目的新对话。旧对话以通用对话显示。

**契约。** 给助手会话加可空 `projectId`，创建时验证项目，随后由后端按会话读取。每轮上下文分别渲染「会话项目」和「当前页面」。项目被删除时显示明确状态，并提供新建对话入口。需要项目的工具由操作契约确定字段，创建任务等操作在确认卡上展示实际提交的项目及分支。协议与 `aw-task-requirement` 写明「这个项目」优先使用会话绑定的项目，通用对话沿用当前页面上下文。在已绑定会话里明确要求切换项目时，提供开启对应项目对话的入口。

**验收。** 两个项目的集成和浏览器回归覆盖预选、通用对话、首次发送、页面切换、重启恢复和项目删除。在 A 项目会话切到 B 项目页再说「在这个项目建任务」，上下文和确认卡都应指向 A。真实模型验证能正确读取会话项目、使用项目相关工具。

### UX-05 续接助手对话

**界面。** 在主页和侧栏的会话菜单加「续接对话」。由应用识别提供方明确的上下文超限错误，在失败消息旁提供同一入口。新对话标明来源和续接时间，可展开浏览截至续接时的旧消息。超限失败的用户输入带到新对话输入框，用户检查后发送。续接前可勾选需要带过去的附件。

**会话和历史。**

- 建立独立的应用会话和模型会话，继承项目归属，持久化来源和历史截止位置。完整历史按需从原会话读取。原会话删除后显示来源不可用，已持久化的交接内容保存在新对话里。连续续接时单次浏览或注入均按明确的历史范围处理。
- 首次发送携带有长度上限的交接内容，根据模型已知的上下文容量为首条用户消息和回复留出空间。摘要写入已经确认的决定、任务编号和尚待处理的事项，并保留最近几轮原文。复用 `assistant.recovery-context.ts` 的可见文字提取，单独定义续接用的历史提示。生成摘要需要调用模型时使用新的独立请求。摘要生成失败时，由近期原文提供可用的交接内容，并在界面标明只带了近期消息。首轮发送确认后只消费该次交接内容一次。
- 附件通过附件服务为新会话显式建立归属。权限、确认卡、预览绑定、应用回传和用量各自按原有会话归属处理。交接内容标注为历史资料，当前状态通过任务工具查证。续接请求按同一次用户操作去重，异常时可重试，避免创建多个可见副本。

**助手验收。** FakeOpencode 模拟明确的上下文超限，验证点击后模型会话 ID 变化，原历史可读，待发送消息可编辑，附件仅限选定项。集成覆盖未发送就重启、摘要失败、原对话后续新增消息、原对话删除、重复点击和带待确认卡的原对话。真实模型用相隔较远的已确认决定和任务编号验收续接效果，检查新轮会根据工具结果更新旧任务状态。

浏览器实测截图：[浅色主题 · 选择附件并续接](assets/43-workflow-experience/continue-light.png)、[深色主题 · 侧栏查看来源消息](assets/43-workflow-experience/continue-dark.png)。真实 OpenCode 与本地脚本模型验证了首轮只发送一次交接，且包含绑定项目、较早的决定和任务编号。

### UX-08 项目详情页的常用入口

**界面。** 项目页头以「开始任务」和「问这个项目」为主要操作。项目概览展示近期任务，优先提示失败、待处理和待合并，提供去任务列表查看本项目的入口。「做成 PPT」放入次级操作。UX-07 的最近运行检查结果可在项目概览里打开。

**验收。** 浏览器从 A 项目页两条入口分别打开已预选 A 的任务编辑和助手新会话。最近任务只列 A 的结果，更新状态后显示一致。简单模式和专业模式均能一步打开项目常用操作，小窗口中已有配置仍可访问。

## 4. 启动检查、模板与远端交付

### UX-06 单个任务的 AI 执行计划存为流程模板

**界面。** 在有 AI 执行计划的待确认任务页和已完成结果页提供「存为流程模板」，进入预填的新建流程编辑器。界面显示来源任务和计划版本。沿用自定义流程的专业模式规则，保存为固定流程后可在「直接开始」的自定义列表选择。多阶段需求计划使用已有的组合模板编辑器，按钮明确写「存为组合模板」。

**转换。** 按指定版本读取计划图中的业务步骤、角色、依赖和计划层检查，沿用现有 `workflows.validate` 与 `workflows.create`。以业务步骤间的依赖生成固定流程，可复用的项目检查沿用现有项目检查占位符。任务运行时追加的核验、重验、交付冲突处理或修订步骤由对应任务功能在新任务中产生。编辑器提示用户检查需求文字、绝对路径、分支与项目特有命令，并提供步骤预览。保存形成独立的流程版本。

**助手与验收。** 助手收到「把这份计划存为模板」时，按来源打开对应的预填编辑器。`aw-task-requirement` 在推荐流程时查询已有自定义流程。集成验证读取准确版本、依赖和角色校验、缺失角色提示以及生成步骤正确处理。浏览器从待确认与已完成任务进入编辑器，保存后用另一份需求创建任务，检查实际运行的业务步骤、角色、依赖和项目检查来自正确来源。

### UX-07 项目运行检查

**界面。** 项目详情提供「检查运行环境」，让用户明确选择运行检查的目标分支与项目命令。按仓库与分支、检查命令、已配置预览分别显示通过、失败或未配置，失败带关键输出和跳往对应配置的入口。显示最近一次检查的时间、分支与配置版本。

**执行。** 复用 Git/worktree、检查命令和预览模块，在临时独立工作区运行，遵循原有项目网络、进程、超时和清理配置。已配置的项目命令和预览安装命令在界面显示后由用户点击运行。用户可以停止，退出或失败后收尾。检查进展单独呈现，结果明确区分命令无法启动与命令运行后测试未通过。

**验收。** 真实 Git 测试覆盖分支错误、依赖缺失、命令退出非零、预览启动失败、用户中止和进程及临时工作区清理。浏览器走通「检查失败 → 跳至设置改正 → 重新检查通过」。用目标 Windows 和 Linux 环境补测路径、进程清理及项目配置读取。

**实现记录。** 检查保留所选分支、配置版本和已确认命令的快照；项目被删除时中止检查。正常退出时等待进程及工作区清理，启动时根据数据目录中独立保存的清理记录重试遗留工作区；仓库不可达时保留记录以便下次重试，并将清理错误作为独立诊断展示。检查命令区分无法启动、超时、非零退出与执行错误。已有 CI 矩阵包含 Windows 与 Linux 的集成及浏览器用例，目标环境实际结果以运行记录为准。

### UX-09 PR / MR 状态回流

**界面。** 任务结果保留平台链接，增加「刷新交付状态」。按平台可提供的信息分别显示远端请求状态、CI 和审查，以及最近成功查询时间。请求失败给出原因，保留带时间的上次查询结果。需求计划区分「远端待合入」「已远端合入，等待本地分支包含交付结果」与「可以确认已合入」。

**服务。** 扩展 `hosting` 的 GitHub / GitLab 适配器，按已记录的远端仓库和 PR / MR 标识查询，兼容只有 URL 的旧交付。CI 和审查按当前 head 提交归属，凭据和代理沿用现有服务。远端已合入由平台状态确认。本地是否可用于下一阶段按需求计划的基础分支和可验证的合入提交判断，考虑 squash 和平台变基后的提交。状态回流首版提供读取和提示，沿用现有「已合入」确认与阶段依赖。

**验收。** 仿真平台集成覆盖待审查、CI 等待和失败、推送新提交后的状态变化、合入、关闭、权限不足和网络不可用。真实 Git 验证远端已合入但本地尚未拉取、分支包含真实合入提交等情形。发布验收分别在授权的 GitHub 和 GitLab 测试仓库验证刷新和审查意见回流。

### UX-10 知识问答据此开始任务

**界面。** 在已有答案处增加「据此开始任务」，让用户预览选中的结论和引用、修改需求并选择流程，再进入现有开始任务表单。任务详情可返回来源问答及所选轮次。

**来源。** 来源项目由问答记录确定。服务端按已验证的回答读取用户选中的结论和引用，生成受限的资料快照，经现有附件归属绑定到任务。在快照中保留出处、时间和可定位的信息，明确数据库记录或网页摘录的来源，允许用户在预览中去掉无需带入的内容。按任务正文的资料边界处理旧答案和摘录。

**验收。** 浏览器从带文件和网页引用的答案启动任务，表单有正确项目和选中的内容，任务能打开快照并返回具体答案。测试取消表单、切换流程、来源被删除和未选中引用排除后的行为。

**实现记录。** 从已校验的回答中选择至多 8000 字符和任意一组已有引用，服务端生成文本附件。任务表单沿用来源项目，可切换单任务流程和继续修改需求。任务成功创建后附件依任务归属保存。原问答删除后仍可读取快照。跨项目创建拒绝绑定该资料。

## 5. 从任务结果回到需求与项目约定

### UX-11 需求覆盖关联到核验证据与交付

**界面。** 延伸需求计划现有覆盖表。展开某个原始需求时，可看到关联工作包、当前任务、对应验收项、用到的核验证据和本地交付提交或远端 PR / MR。分别呈现「已拆分」「已核验」「已合入」等事实。人工接受、待核验、清单版本过期与工作包放弃均按真实状态显示。

**数据。** 沿用现有「原需求点 → 工作包」映射，逐步增加「工作包的需求点 → 任务验收项」的稳定引用。有明确关联时显示逐项链路，旧工作包只建立工作包级关联。批量加载任务结果和交付摘要，保留历史版本，当前任务被替换时能区分上一次与本次交付。

**验收。** 两阶段需求计划中从原始需求点击到任务验收项，再打开证据和最终提交。覆盖一个需求分到多个包、需求未实现、旧数据只有工作包映射、工作包重试换任务、远端未合入和验收结论过期。

**实现记录。** 拆解工具可为包内验收项给 key，并在覆盖行显式引用；服务校验后将引用保存为验收项 UUID。工作包启动记录每次任务，拆解保存覆盖与工作包身份快照。页面批量读取任务、各清单项最后所在版本和结论、最近交付，旧记录只显示已知的工作包级关联。升级时可补录当时的当前任务与最新覆盖表，升级前已被覆盖的任务及旧覆盖版本不可恢复。任务删除保护覆盖所有已记录的包任务。


### UX-12 将失败经验和审查意见整理为项目约定

**入口。** 从质量页已经钻取到的失败任务及任务详情的审查意见，提供「整理为项目约定」。先让用户选中相关失败或评论，再预览建议、来源任务和适用范围。项目环境的检查、预览等问题可打开相应项目设置，团队长期约定可作为说明发起现有 `AGENTS.md` 补充任务。

**边界。** 用户明确选中的事实和意见作为资料传入。助手提出可复用的约定时写出证据和适用条件，用户审核后在配置界面提交或按现有交付方式合并。按项目过滤证据并保留来源标记。

**验收。** 从同一项目选中两条失败与一条审查意见，预览能定位原记录。确认后创建包含所选内容的 `AGENTS.md` 任务，合并后项目页可见新增规则。覆盖一次性任务要求、跨项目证据和取消操作。

**实现记录。** 失败按任务事件 ID 选取，审查意见按任务和评论 ID 在预览时读取；服务端核对项目归属，快照绑定现有 `system.agents_md` 任务。失败类型生成待核对的规则提示，审查意见提供可编辑摘录，用户填写适用条件；这不是模型对根因的判断。一次性问题可直接退出，取消会删除临时快照。每条资料最多 8000 字并隐藏常见凭据格式，预览显示实际内容；旧失败事件未保存的详情明确标记不可恢复，新事件只保存检查类型和结果，不复制命令输出。浏览器通过 FakeOpencode / FakeHosting 走通两次失败、一条评论、预览及合并，并验证取消和一次性退出；跨项目拒绝与预览后评论变化由集成测试覆盖。

## 6. 实施与发布验收

- 按 [06 · 代码开发规范](06-coding-standards.md) 和 [07 · 测试规范](07-testing-standards.md) 提交。新增操作进入共享注册表，写操作标注风险、模式和助手暴露范围。任务与节点状态经状态机更新。新增迁移需用真实 SQLite 验证从已有数据升级后的读取、重启恢复及旧记录兼容。
- 接口和状态机有改动时同步更新 08–12，界面更新 14，助手更新 15 与相关内置 skill，各功能的设计记录随对应实现更新。项目归属、续接历史的解释和写操作确认放在应用契约与协议提示词，操作选择细节更新 `aw-task-requirement` 和 `aw-task-diagnosis`。提示词改动附真实模型用例对比。
- 每批先通过相关测试，再跑 `pnpm verify` 和该批浏览器 E2E。涉及助手生命周期或协议时补 opencode 与真实模型验收。发布前对升级后的测试库跑一次组合旅程，并按现有发布流程验收目标平台。
- 结果以可观察行为核对。重验成功时原开发尝试数可核对，续接后能说出已确认约定并查到当前任务，已交付结果能定位到原证据与提交。真实平台、企业网络或真机未验证的场景在发布记录里按实际情况登记。
