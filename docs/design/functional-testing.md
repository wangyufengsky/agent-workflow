# 内置工作流「功能测试」设计草案

用户选择项目和功能模块，描述想验证的行为。测试工程师据此编写用例，在指定版本和环境中执行，交付可以逐条核对的测试报告。建议工作流标识为 `functional_test`，采用固定阶段、按模块生成用例、以报告交付。首版面向 HTTP 服务和有网页入口的项目。

## 从建任务到看结果

| 阶段 | 用户看到什么 | 工作流做什么 |
| --- | --- | --- |
| 选定范围 | 必填项目与模块描述。可附需求、验收条件、入口地址和已有用例 | 沿用任务的基线选择。默认使用任务工作区的项目启动配置，也可指定已运行的测试地址。列出本轮环境及允许写入的方法和路径 |
| 编写用例 | 一张「行为、用例、预期」表，可调整范围或补充业务规则 | 结合需求、项目文档、已有用例和模块入口，选择主流程、异常输入、相关边界与状态变化。记录每个预期的依据。只有代码可供参考时，标出推断，用当前实现描述的行为不能独立证明需求已满足 |
| 准备环境 | 显示被测版本、服务地址、启动进度和日志。如果测试地址由用户提供，注明版本来源 | 在任务工作区启动服务，或连接已有环境。先检查服务可达，再检查用例需要的条件，例如测试账号、依赖和初始数据。按条件等待并设置截止时间。一个条件缺失，只阻塞依赖它的用例 |
| 执行与观察 | 当前用例、正在执行的步骤、预期与实际同屏。可展开请求、服务输出、浏览器控制台及页面画面 | 接口用例直接发请求并核对响应及后续状态。页面用例用内置浏览器操作，检查可见结果，必要时刷新或重新查询。独立用例在其他用例失败后继续执行 |
| 交付报告 | 总览显示结论和各状态数量，点开失败项即可查看复现步骤及证据 | 先保存执行记录，再从记录生成报告。退出或取消时释放本轮启动的服务，保留已收集证据，列出未完成项。对接入的已有服务只结束本轮连接 |

建议默认自动推进，沿用任务已有的确认和提问机制。已有需求足够明确时可直接开测。影响判定的业务规则缺失时，优先执行预期明确的用例，对其余项集中提问。需要人工登录时，网页用例沿用同页签接管与恢复。

## 内置角色「文档处理员」

建议在角色库中注册 `document_processor`，沿用已有的执行者基类，工作流可直接把文档步骤分配给它。它负责读取资料、提取结构、编写文档、按用户意见编辑并交付新版本。在普通文档任务中，助手可以把「把这份 Word 第三节写清楚」或「在这份 Excel 里补一列说明」交给文档处理节点。节点记录输入文件、目标位置、修改摘要和产物版本，用户可以查看正文并继续提出修改。

| 功能测试节点 | 负责人 | 交付给下一步的内容 |
| --- | --- | --- |
| AI 编写案例 | 测试工程师 | 根据需求设计的内部用例、覆盖范围及断言依据 |
| 解析上传案例 | 文档处理员 | 从原文件提取的同格式用例 v1、原文位置和缺失项。执行能力、账号或环境条件由测试工程师在准备环境时核对 |
| 准备环境、执行与复测 | 测试工程师 | 带用例版本、断言、实测值与证据的执行记录；需修正转写时引用原文件发起修订 |
| 编写测试报告 | 文档处理员 | 用执行器汇总的数据和测试工程师的缺陷说明形成可阅读、可导出的报告。逐项结论和覆盖数由执行记录生成，报告节点可把缺少依据的描述退回补证 |

角色按节点加载适用的 Skill。导入节点使用功能测试 Skill 的案例映射章节及文档读取说明；文档编辑节点复用 `aw-artifact-revision` 的版本流程，配置可见的文档读写指南。读取任务附件用 `read_attachment`、`read_sheet`，读取项目内 Office 文件用 `read_office_file`。文档任务中按格式复用已有的文本、Word、Excel 发布与编辑工具，生成新版本并读回核对。Word 重建或 Excel 往返发生格式损失时，向用户指出具体受影响的内容。测试报告通过本流程的报告提交工具发布；文档任务专用写工具保持其现有作用域。

## 上传已有案例

建任务时选择「AI 编写案例」或「使用我上传的案例」。后者可一次上传多份文件，或从项目助手对话中选取已上传的附件作为案例来源。需求说明、接口文档等其他附件仍可作为参考资料。根据用户的选择，任务计划中的第一个用例节点为「编写案例」或「解析上传案例」。两个入口都产出同一种内部用例，随后进入相同的准备环境、执行测试和测试报告节点。

| 案例格式 | 解析方式 | 在用例中保留的位置 |
| --- | --- | --- |
| Markdown（.md）、文本（.txt） | 用 `read_attachment` 分页读完，识别标题、编号、列表、表格及多行步骤 | 文件名、原编号、行号或原文摘录 |
| Word（.docx） | 读取附件提取的正文，按标题、段落及表格组织步骤，将同一用例的多行内容归在一起 | 文件名、章节、表格行或可核对的原文摘录 |
| Excel（.xlsx） | 先列出工作表，再用 `read_sheet` 分段读取案例所在区域。按实际表头映射字段，支持每行一例及多行组成一例 | 文件名、工作表、单元格范围及原用例编号 |

沿用项目的 Office 导入约定。旧版二进制 .doc 和 .xls 提示另存为 .docx 或 .xlsx。遇到内容无法提取、依赖图片判定或表格归属不明，按文件及位置列出需要补充的内容。

**节点产出。** 每条内部用例都有独立 ID 和版本，保留原编号、标题、前置条件、数据、有序步骤、逐步或最终预期，以及指向原始附件的引用。比如工作表「订单」的 B12:F14 是编号 ORD-07 的一条三步骤案例，导入后只生成一条 v1，保留三个步骤及其原始位置。启用导入模式时，按用户提供的案例执行；用户另有补测要求时，新增用例标为 AI 补充。

**解析现场。** 左侧按读取顺序增加案例名，大窗口展示选中案例的标准化内容，可对照原文。每个文件汇总已识别、可执行及待澄清条数，并列出未能识别的区域和原因。缺预期的案例保留为待澄清，助手可在对话中询问，其他完整案例照常推进。文件自带的「上次通过」等历史结论只作为来源资料，本轮结果取自实际执行。解析阶段只读取和整理材料，文档内的请求或命令作为用例步骤，在后续已授权环境中执行。

**版本与衔接。** 解析进度和来源一同保存。同一解析节点中断后按原附件和位置继续，避免重复建例；不同文件的同名用例保留各自来源。用户明确写出的验收预期进入 v1。后续发现转写错误时，引用原文创建修订；要改变用户的原始验收要求时，沿用业务规则澄清流程。报告、修复任务和复测记录均可追溯到原始案例。

## 用例怎样执行

每条用例记录编号、对应需求、前置条件和测试数据、操作入口、步骤、可观察的预期及清理方式。执行时另存本轮实测值、判定和证据。预期在操作前确定，修改预期需保留版本。项目内已有匹配的回归用例可直接引用。首版保存可复跑的任务用例，按项目提交自动化测试代码可留给后续独立交付。

下面以「待办事项完成后，刷新仍显示已完成」为例。表中是用例设计，实际值由执行器填写。

| 用例 | 操作 | 通过条件 |
| --- | --- | --- |
| FT-01 完成并刷新 | 创建本轮专用的未完成事项，在页面点击「完成」，刷新后按事项 ID 找回同一条记录 | 刷新前后均显示已完成。记录该次更新请求与刷新后的页面断言，便于区分界面更新和持久化问题 |
| FT-02 非法状态 | 通过接口为本轮另一条事项提交约定范围外的状态，再读取该事项 | 响应符合项目接口约定的校验错误，原状态保持不变。按预期返回的错误响应计为通过 |

如果 FT-01 更新请求成功、刷新后却恢复成未完成，记录失败步骤、事项标识、实际状态及相关请求。服务日志用于定位原因，报告中把观察事实与可能原因分开。如果缺少测试账号，FT-01 记为阻塞，具备独立前置条件的 FT-02 继续运行。

## 执行中修订用例

允许 AI 在执行中纠正用例。先保存原执行及其证据，再判断问题归属。每次执行绑定一个不可变的用例版本；修订单独生成新版本。其他独立用例继续执行。

| 发现 | 处理方式 |
| --- | --- |
| 用例写错了字段、取错了测试数据，或操作了错误的页面元素 | 有独立依据证明错误、业务意图和验收标准保持一致、操作仍在授权范围内时，AI 可直接修订并复测。例：接口契约定义字段为 `done`，请求却发送了 `state`，因此触发了未知字段错误，原本要验证的非法状态还未测到 |
| 用例把已确定的预期抄错 | 例如该版本的已确认接口契约写明创建成功返回 201，用例误填 200。AI 可引用契约的版本与位置直接纠正，并保留第一次的原始断言结果。如果依据只有本次实测值，或验收需求另有约定，则交给用户澄清 |
| 改动会改变业务预期、放宽断言、删减覆盖，或需求与接口约定相冲突 | 助手展示差异、依据和影响，请用户在对话或现场明确采用哪条规则。确认前保留原断言与实测，受影响项显示待澄清。如果用户决定改变需求，报告注明验收标准发生了变化 |
| 预期有明确依据，实际行为与之冲突 | 保留功能失败并提供「建立修复任务」。实际响应本身不足以作为改写预期的依据。若缺少环境条件，记录阻塞原因；若归属尚不明确，列出仍需核实的证据 |

**现场。** 用例编号保持稳定。时间线显示「v1 执行 → 修订 v1 至 v2 → v2 复测」，展开修订可看具体字段的前后值、原因、依据的文档位置或证据事件、作者与时间，以及受影响的步骤。助手可以读取这份记录，也可按用户说明提出修订。执行和报告均能回看旧版及原始输出。

**复测。** 同一被测版本、同一环境上，重新准备独立数据，从受影响的前置步骤开始执行，必要时重跑依赖用例。可能产生副作用的请求先核对上次的提交结果。新版再次出现同一问题且没有新证据时，停止自动修订，记录未决问题。若程序版本也发生变化，单独注明，不能把差异归因于用例修订。

**报告。** 按用例编号统计覆盖数，按版本列出每次执行。旧版因用例问题未测到目标行为时，标明「阻塞 · 用例问题」及当时的实际输出。新版本已创建但尚未执行时显示待复测；执行后再给结论，例如「通过（修订后复测）」。另列用例修订数量，并与产品缺陷的数量分别统计。

## 结果与证据

- **通过**需要每个必需断言都有实测值且满足预期。**失败**表示已观测到与预期相反的业务行为。**阻塞**表示环境、数据、权限或证据不足以完成判定。**未执行**表示取消或停止时尚未开始。没有接口或 UI 的步骤可只保留适用的证据。
- 一轮报告列出基线、环境、范围、各状态数量、逐项预期与实际、缺陷复现、阻塞原因及未覆盖行为。全部在范围内的用例通过才显示「全部通过」。同时存在失败和阻塞时，两项都显示。任务正常产出报告即可完成，业务用例发现缺陷也能正常交付。
- 证据按运行、用例、步骤关联。HTTP 记录方法、路径、状态和断言用到的响应字段。页面记录实际文本、状态、相关请求或截图。服务记录相关时间段的标准输出和标准错误；外部环境未接入服务日志时标明可用证据。日志和响应限长，认证头、Cookie、令牌等在持久化前脱敏。
- 支持有意发起的新一轮复测，重新准备独立数据并保留两次结果。写请求遇到超时且提交结果不明时，先用可读状态核实，证据仍不足就记为阻塞。每轮跟踪本轮创建的数据及清理结果。

## 四个阶段的主视图

| 阶段 | 主窗口 | 交互 |
| --- | --- | --- |
| 编写案例 | 小窗列出已写出的案例名，大窗显示选中案例的前置条件、数据、步骤、预期结果及依据 | 第一条命名后即可阅读。后续每新增一条就追加到列表，补写同一条时就地更新正文。默认跟随 AI 编写，点选旧案例后保持阅读位置，新案例继续增加；点「跟随编写」回到最新一条 |
| 解析上传案例（上传入口的第一阶段） | 同一列表逐条展示解析出的用例，大窗显示内部字段、原编号和出处 | 可对照原文或定位到待澄清项，手动选中后保持阅读位置 |
| 准备环境 | 整个主窗口展示 AI 操作，按发生顺序列出读取配置、启动服务、检查依赖及核验数据等动作 | 点击有详情的动作查看命令、输出或失败原因。活动直接在主窗口呈现 |
| 执行测试 | 用例滚轮、对应行为与结果终端 | 按下节的自动跟随与手动回看规则联动 |
| 测试报告 | 沿用文档任务的正文预览。打开即阅读报告，写入时跟随正在生成的章节，完成后保留完整正文 | 在正文阅读测试范围、环境、逐项结果、缺陷复现及证据，失败项可建立修复任务。导出与当前查看的报告使用同一版本 |

编写阶段以用例稳定 ID 接收新增和更新事件。重连后先还原已保存的列表与正文，再接收后续增量；测试执行时引用编写完成的用例版本。编写时手动阅读旧案例的选择与执行时五秒回到实时的规则各自独立。

## 各工作台共用的 AI 活动

代码改动、方案、审查、文档和网页工作台使用同一活动组件。卡片标题展开或收起执行过程，动作行沿用流程节点的交互，失败动作可展开错误，专业模式可展开工具输入与输出。标题旁的「完整详情」即使卡片已收起也可点击，并定位当前选择的步骤和执行轮次。没有节点的任务级活动打开该次执行的记录。历史步骤和当前步骤都使用同一入口。

## 测试现场

[打开可交互的测试现场示例](functional-testing-preview.html)。示例使用本地演示数据。产品中的现场放在任务工作台里，与既有的任务现场和流程画布沿用同一导航。进入就能看到正在测什么、做了什么、结果如何。

| 区域 | 呈现与联动 |
| --- | --- |
| 用例滚轮 | 用例按计划顺序纵向排列，当前项居中放大，上下保留相邻项。每行显示编号、用例名、运行状态。收到下一条用例开始事件后滚到新位置。滚动、点选和键盘方向键均可回看；视窗中心的用例就是正在查看的用例 |
| AI 测试行为 | 按所选用例展示已经发生的操作。HTTP 行先显示方法、路径和「等待响应」，收到响应再补状态码、耗时及脱敏字段；浏览器行显示点击或输入的目标，查看日志行显示读取来源。可展开某一步定位对应证据 |
| 结果终端 | 按所选用例展示带时间、步骤和来源的实测事件，例如服务输出、Console、响应字段、断言的预期与实际。正在运行的用例随新事件追加，已结束的用例显示完整记录，待执行的用例只显示计划与等待状态 |

跟随时，运行位置决定选中项。用户手动滚动即进入回看，行为与终端一起切到所选用例，测试继续执行。顶部持续显示真正正在执行的编号，并提供「回到实时」。建议最后一次操作后 **5 秒**自动跟回最新执行项；滚轮、键盘、终端滚动或展开详情均续时，拖动、选取文本、操作对话框期间暂停计时。任务结束后停留在用户查看的位置，允许自由回看。减少动态效果模式直接定位，保留相同的选中反馈。

宽屏执行现场分为三栏。左栏滚动选择用例，中间查看该次执行的请求、预期与实际断言及结果终端，右栏展开活动或打开完整详情。窄屏按阅读顺序排列。选中、焦点、状态、表单和终端使用当前应用皮肤的颜色令牌。

执行端按轮次、用例、步骤和递增序号发布已持久化事件。三个区域和助手查询使用同一份记录。切换用例时按其标识读取历史，迟到的响应归回原用例。重连从最后序号续读。服务全局日志按来源和时间窗作为上下文展示，只有可关联的行标为该用例证据。

## 从测试结果建立修复任务

已判失败的用例在现场终端和最终报告都提供「建立修复任务」。用户可立即为一条失败项建任务，也可在报告中勾选多个用例合建一个修复任务。阻塞项显示具体缺少的条件及恢复入口。

复用内置「修 Bug」工作流，创建时携带项目、被测基线、测试环境、来源任务与运行轮次、用例版本、复现步骤、失败断言的预期和实际、脱敏证据链接，以及修复后应复测的用例。相同创建请求重复提交时返回已建任务。两边都能点回对方，助手和用户看到同一关联。多个用例合建时逐项保留复测要求。

修复形成可测试的提交后，用户或助手可选择「用修复版本复测」。新轮次明确显示实际被测版本，沿用同版用例，在新数据上执行，报告并列原失败与复测结果。修复任务的完成状态和用例复测结论分别展示。连接外部测试地址时，若修复版本尚未部署或无法核实，显示环境待更新或版本未核实。

## 助手全流程操作

用户可以在项目对话中说「测一下待办完成和刷新，发现失败就建修复任务，修好后复测」。助手识别项目、模块、测试目标和后续动作，在对话中呈现已有确认机制所需的范围，然后建任务。测试执行器负责启动服务、运行用例和收集证据；用户可以一直停留在对话中，也可随时打开现场。

| 用户意图 | 助手可完成的操作 |
| --- | --- |
| 发起与调整 | 创建测试、查看或调整待执行的用例、补充数据或需求、开始或取消执行。需要确认测试写入范围时，在对话卡显示目标和方法／路径，绑定该次确认的参数 |
| 跟进与恢复 | 查询运行进度或指定用例，读取具体请求、断言与日志证据；遇阻塞时说明缺什么。需本人登录时从对话直达接管页签，完成后从原步骤继续 |
| 交付与修复 | 获取及导出报告，按用户指定的失败项创建或查看关联修复任务，在修复版本可用时发起复测并返回两轮对比。用户已在任务中指定的后续动作由持久化任务关联驱动，关闭对话后仍可继续 |

这些动作注册为界面和助手共用的操作，沿用项目绑定、凭据处理与写操作确认。当前浏览器测试的助手入口会引导用户打开表单确认范围，功能测试需要补上等价的对话内确认与提交。助手可回答「FT-01 哪一步错了」并附具体事件，也可将现场打开到指定轮次和用例。

## 首版落地

### 内置 Skill 怎样进入任务

建议新增执行端 Skill `aw-functional-testing`。用英文编写，包含从需求写可执行用例、选独立断言依据、准备与清理数据、运行 REST 和页面步骤、区分产品问题与用例问题、修订后复测、提交带证据的报告。内置示例并排展示两种情况：契约字段抄错，可修订后复测；刷新后状态丢失，保留失败并交接修复。每个阶段的节点指令都明确要求先读任务上下文、加载该 Skill，再使用本阶段工具。恢复会话时先查已保存的执行位置，尤其是已发出但结果未知的写请求。

现有执行者的 Skill 配额已用满（9/9）。按工作流为功能测试会话提供专用集合，保留提交指引、页面检查等适用 Skill，将前后端开发专用 Skill 的名额用于功能测试。助手的配额同样已满（10/10），在已有的 `aw-task-requirement` 中增加功能测试任务的识别与发起说明，在 `aw-task-delivery` 中增加读报告、建修复和复测的示例。这样仍可用一句话调度全流程。Skill 管理页、会话可见列表和实际白名单需从同一分配规则生成。

### 工具与回执

以下是拟新增或扩展的契约。执行端工具沿用项目的 MCP 前缀，此处省略前缀。工具描述包含调用时机、必填参数、可观察的效果，以及失败后可采取的下一步。任务、会话和当前阶段由后端确定。

| 阶段 | 工具 | 输入与可验证的回执 |
| --- | --- | --- |
| 进入或恢复 | 扩展已有 `get_task_context` 与 `get_submission_guide` | 上下文返回授权范围、当前阶段、未完成用例和可用操作。提交指引给出当前阶段的提交入口、参数示例，以及上一次被拒的具体字段 |
| 编写案例 | 新增 `test_case_save` | 每次保存一条草稿或补写既有草稿。输入需求引用、前置条件、步骤、断言及依据，返回稳定的用例 ID 和版本。成功保存即产生工作台可见事件。已执行的版本只接受修订 |
| 解析上传案例 | 复用 `read_attachment`、`read_sheet` 和 `test_case_save` | 任务上下文列出用户指定的案例附件。功能测试 Skill 的导入章节指导模型完整读取、映射字段、保留原意、标记歧义。保存工具接收来源附件、原编号、位置及待澄清字段；节点提交回执列出每份文件的处理情况与遗漏区域 |
| 准备环境 | 新增 `test_environment_prepare` | 在已确认目标上启动或连接服务，复用进程托管。返回环境标识、实际基线、就绪检查和日志引用。测试结束或取消时由任务回收本轮资源 |
| 执行及复测 | 新增 `test_case_run` | 输入用例 ID、指定版本和环境。执行器按保存的步骤发送结构化 HTTP 请求或调用已有浏览器动作，记录请求、响应、DOM、日志与断言实测值。返回执行 ID。重复传递同一次执行标识只取回原执行；有意复测会产生新执行 ID |
| 查看实况 | 新增 `test_run_read` | 按运行、用例、步骤或事件游标查询进度、原始结果、服务日志片段及浏览器证据。用户问“刚才发了哪条请求”时，助手和现场引用相同的事件 ID |
| 修订 | 新增 `test_case_revise` | 输入原版本、字段差异、原因、独立依据及触发它的执行 ID。返回新版本或待澄清事项。后端核对原版本及证据归属，比较覆盖范围和断言，保留原始执行。涉及业务规则变化时，对话中的确认绑定到这份具体差异；旧版本冲突时先读取最新记录 |
| 交付 | 新增 `test_report_submit`，接入既有提交指引 | 输入本轮实测引用、缺陷解释及未覆盖范围。后端按执行记录计算计数和结论，拒绝引用错误轮次或把缺少证据的项写成通过；有失败或阻塞也能发布报告，返回可阅读的报告版本 |
| 报告后续 | 界面和助手共用操作清单 | 扩展任务创建以接受功能测试范围；提供读运行／报告、按失败项创建关联修复任务、指定被测提交复测的操作。助手取得任务或运行引用后跟进，复用现有确认、取消与提问机制 |

例如修订工具收到“将预期状态码从 200 改为 201”时，若引用的是本次响应，只能返回待澄清以及缺少的依据。若预期由已确认、适用于该基线的结构化接口契约唯一确定，服务端可对照对应操作和状态码后生成 v2。文本材料存在解释空间时保留差异供用户决定。工具成功只代表新版本已保存，随后运行 v2 的实测结果才决定结论。

验收分两层：集成测试验证版本留痕、幂等执行、授权范围与报告统计；真实模型从一句“测这个模块”开始，在工具调用记录中验证加载 Skill、逐条保存用例、读取失败证据、修订或提交产品缺陷、复测及报告提交。用例契约抄错与实现确实有缺陷应放在同一组场景里，检查模型能作出两种不同处理。只检查 Skill 文件存在或工具注册成功不足以验收。

### 工作流接入

| 复用或新增 | 设计决定 |
| --- | --- |
| 复用内置流程与角色 | 沿用报告型交付和测试工程师角色，在固定流程里串接用例设计、环境准备、测试执行与报告。浏览器测试继续承接用户已给出网页步骤的任务 |
| 复用服务与浏览器 | 本地单服务复用任务预览的进程托管、端口分配、停止和日志。现有浏览器动作、DOM 断言、控制台警告与错误、异常、网络摘要、截图和写入范围规则继续使用。现有预览探针收到 HTTP 响应即可就绪，功能测试另按场景验证所需条件 |
| 新增直接 HTTP 测试 | 为当前任务的测试目标发送结构化请求，支持 JSON 请求、响应字段断言、引用前一步生成的 ID。沿用目标地址和写入范围约束，重定向后继续校验目标。首版支持一个项目启动命令或一个已有测试入口，可覆盖纯后端项目 |
| 新增模块测试报告 | 一条用例可关联浏览器步骤与直接 HTTP 步骤。执行器保存实测值和证据引用，服务端按断言汇总状态。测试工程师提供复现说明与覆盖缺口，文档处理员组织并发布正文。任务页展示结果，支持导出同内容的 Markdown 报告 |

首版验收使用一个带 HTTP API 和页面的小项目。分别走通纯接口测试、页面操作后刷新核验、已知缺陷生成失败报告、服务启动失败生成阻塞报告、运行中取消并回收进程、复测保留历史。验收时打开报告里的证据验证其确实对应失败步骤，同时确认接入已有服务的任务结束后该服务仍可访问。

首版还须走通以下用户路径。

1. **现场联动**。FT-02 正在运行时滚到 FT-01，两个详情区只显示 FT-01。FT-02 后台收到响应，FT-01 的终端仍显示自己的记录。持续操作会续时，空闲 5 秒回到最新用例，也能立即手动返回。完成后可稳定回看。
2. **修复闭环**。从一条真实失败断言创建修复任务，再从报告重复打开，得到同一任务；按修复版本复测后能同时查看旧失败和新结论。
3. **对话走通**。从项目助手发起测试，在对话内确认测试范围、查看用例进展、读取报告、创建修复和发起复测。验证助手返回的用例、版本与现场一致，已安排的后续动作在重新打开对话后仍可查询。
4. **用例修订**。错误字段触发错误分支，AI 依据接口契约修订，新版复测后汇总为一条用例，报告可回看两个版本的真实输出。另用一个真实功能缺陷检查原断言得到保留；涉及业务预期的待确认修订在确认前不参与复测。
5. **上传用例**。用 Markdown、TXT、含表格的 Word 和多工作表 Excel 从任务表单及助手对话发起测试。验证跨行用例保留顺序和预期，缺预期项可定位原文，两份文件的同名项不会覆盖，分页或中断恢复后数量准确。用同一条案例分别从导入和编写入口执行，核对两者走同一执行器，导入报告中的来源可以回到对应行或段落。

多服务编排、项目级跨任务用例库、按提交自动回归可在首版获得真实使用反馈后安排。
