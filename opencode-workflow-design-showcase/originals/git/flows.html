Git 仓库 · 操作逻辑与流程

这一页把「Git 仓库」页的结构、前置判定、浏览、AI 审查、一键修复、提交 / 推送 / 合并与状态流转画成图。界面不直接执行 git，所有读写都经应用服务调用内部 MCP（git / gitlab），目前接口均为候选，待接入。原则只有三条：审查只读、修复只写隔离的修复分支、提交 / 推送 / 合并只在用户点击后发生。

01页面结构

侧栏「Git 仓库」进入仓库概览（所有已登记项目），点「进入」到仓库工作台；从项目页的 Git 徽标点「查看 Git」会直接进入工作台并预选该项目。工作台是三栏：过滤 / 分支 / MR · 提交列表 · 提交详情。

02前置条件判定

进入页面时自上而下判定。Git 能力未接入时整页说明（未知样式，不是错误）；其余按项目判定，每个「否」都给出原因和出路。只缺 GitLab 时仍可浏览本地提交，远端相关功能停用并引导去设置。

03浏览流程

选项目 → 提交列表 → 提交详情 → 改动文件 → diff。左栏分段切到「分支」或「合并请求」时右栏换成对应列表，点分支回到筛选后的提交列表，点 MR 的提交回到提交详情。

04AI 审查流程

审查设置决定范围、维度、职业和上下文；运行中可停止。结果有四种：发现问题、没有问题、失败、结果未知。整个审查只读，不改文件；用户标记与勾选问题后才进入修复。

05一键修复流程

确认后服务基于提交所在分支的最新提交建一个隔离的修复分支和工作副本，AI 只在里面改代码；配置了测试命令就自动校验。结果交给用户决定：提交，或放弃（删除本地修复分支）。

06提交 / 推送 / 合并

三步有先后依赖，不自动连锁：未提交不能推送，未推送不能建合并请求。每步都有守卫：推送被拒只引导「获取远端更新」，永不强推；保护分支只能走 MR；任何写操作回执未知都进入「核对原操作」，永不自动重发。

07谁触发什么 · 责任边界

每一个会改变仓库或远端的动作，都要能回答「是谁按下的」。AI 只读或只在隔离区写；写入 Git 历史与远端只在用户点击后发生；凭据不离开服务端。

AI · 审查只读

读取改动与相关文件，输出问题；不改文件、不建分支。

AI · 修复只写修复工作副本

在隔离的修复分支里改代码，不碰用户当前工作区。

用户提交 / 推送 / 合并

只在用户点击后发生；每步写清后果，不自动连锁。

服务凭据只在服务端

GitLab 令牌由服务保存与使用；界面与 AI 都拿不到。

08修复会话状态机

一次修复会话从「未开始」走到「已合并」或「MR 已创建」。待确认、已提交、已推送都可以放弃；写操作回执未知时停在「结果未知」，核对后才进入实际状态。
