01任务主线状态图

执行与验收、交付是两条并列的事实，由不同的 owner 写入。执行结束只会让交付投影进入「待交付」，任务徽标写「执行已结束 · 等待交付」；所选交付目标全部可信成功、由执行 / 任务状态 owner 结算后，才显示「已交付」。任何结束路径都保留工作区文件。

图例 用户明确操作 服务 / 原 writer 交付投影（非内核枚举） 成功 / 保留 失败 / 需处理 被占用，不覆盖 回执未知 · 只核对 未到达 异常区域 用户触发 系统流转 回执未知

02Git 交付目标与步骤依赖

三个完成目标是依赖完整的目标选择，不是自动授权三步：提交、推送、创建 MR 各有自己的表单和确认框。所选目标的每一步都成功、由服务读回后才算已交付。MR 之后在外部 GitLab 合并，不影响已交付。

图例 用户选择 / 确认 步骤 / 服务 判定 成功 / 已交付 明确失败 / 漂移 回执未知 · 只核对原操作 产品外 · 不影响完成 候选 · API 未冻结 用户触发 该目标不需要的步骤 退回重填 核对循环

03非 Git 应用流程

非 Git 任务把所选变更逐项应用回原目录。检查和预览只读；冲突逐项处理，没有「全部覆盖」；确认后原目录若又变化，对应项被阻塞并重读，已成功项不重做。所选项全部可信成功后才结算交付。

图例 用户选择 / 确认 只读检查 / 服务 判定 已应用 / 已交付 被阻塞，需重读 待核实 · 只核对 未执行 / 保持待交付 不提供 用户触发 确认后漂移循环 核对循环

04工作区保全与清理

任何结束路径都默认保留工作区。清理是用户单独发起的动作：先读清理预览，有阻塞就链到原因；有未交付内容时默认保留，丢弃需要额外知情确认。清理后交付回执仍可读；非 Git 的原目录从来不是清理对象。

图例 结束路径 保留 / 已清理 用户发起 / 确认 服务预览 / 执行 判定 受阻 / 不提供 部分发生 · 只核对 待冻结 用户触发 阻塞 核对循环

✕ 旧 Git 设计中刻意不复用的行为（DESIGN-DELTA §2.3）

  • g54 / g56「直接合并」、旧 API fix.merge — 产品内合并未实现；MR 之后只给「在 GitLab 打开」。
  • g55 流水线 / 审批徽标、g54 评审人多选 — 不是现成能力；评审人显示「当前未接通」，不可选。
  • g50「提交并推送」连发按钮 — 每个副作用独立确认，不自动连发后续步骤。
  • g55「合并后自动清理」 — 工作区不自动清理，清理只能由用户单独发起。
  • g59「重试提交」、g60「重试推送」 — 明确失败且证明无副作用后才「修改后重新提交 / 重新预览推送」；UNKNOWN 只有「核对原操作」。
  • 旧 API「ls-remote 即可结算」「只按 source 找 MR」 — 以 PR16 的 create-only push 与原标记 MR 核对为准。
  • 「AI 审查」「修复」页签与 findings 对照 — 普通任务没有 review / finding 事实，不伪造 GitFixRun。
