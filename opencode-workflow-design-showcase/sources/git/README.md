> **设计样例 · 不连接真实 Git / GitLab / 模型。** 原型中的审查、修复、提交、推送、合并都是本地模拟，不能说明能力已经接通。

## 一、页面结构

- **入口**：侧栏「工作区」新增「Git 仓库」；项目页上受 Git 管理的项目可点「查看 Git」直接进入该项目。
- **仓库概览**（未选项目）：GitLab 连接状态条 + 所有已登记项目卡片。
  - 受 Git 管理的卡片显示：当前分支、领先 / 落后远端、未提交改动、最近提交、打开的合并请求、AI 审查待处理问题。
  - 不受管理 / 路径不可用 / 空仓库的卡片写清原因和出路。
- **仓库工作台**（选中项目）：
  - 页头：项目切换、当前分支、领先 / 落后、上次获取时间、「获取远端更新」、在 GitLab 打开。
  - 三栏：
    - 左栏：提交 / 分支 / 合并请求切换，以及筛选。
    - 中栏：按日期分组的提交列表，带简化图谱和审查徽标。
    - 右栏：提交详情，含「改动文件 / AI 审查 / 修复」三个页签。
  - 窄屏：左栏收成图标条，再窄时提交列表变抽屉。

## 二、操作逻辑

1. **浏览全部只读**。看提交、文件、diff、分支、合并请求、复制 SHA 都不改仓库。diff 支持统一 / 并排、忽略空白、展开上下文、全宽阅读；合并提交要先选对比哪个父提交；大文件截断后可加载全部，二进制文件和重命名单独标注。
2. **AI 审查只读**。在提交详情点「AI 审查此提交」，抽屉里选四项：
   - 范围：对比父提交，或对比目标分支；
   - 维度：缺陷、安全、性能、质量、规范、测试；
   - 审查职业：已发布的冻结版本；
   - 上下文：只读改动，或改动加相关文件。

   审查结果包括：结论、按严重度（阻断 / 严重 / 一般 / 建议）和维度计数、问题列表（可在 diff 中定位）。每个问题可标记为接受、忽略或误报，也可勾选进入修复。同一提交可以多次审查，历史记录保留。
3. **一键修复只在隔离副本里写**。修复前用确认框说明三件事：
   - 在新的修复分支 `ai-fix/<sha>-<日期>` 上修，基于该分支的**最新提交**；
   - **不改动用户当前的工作区**；
   - 由哪个职业修，以及项目配置了测试命令时会自动校验。

   修复结果给出：每个问题修复了 / 部分修复 / 未修复、修复改动的 diff（可按文件撤销）、校验结果。
4. **提交 → 推送 → 合并分三步，用户逐步确认，不会自动连锁**：
   - **提交修复**：提交信息由 AI 草拟、可编辑；作者取自 Git 账号设置；可只勾选部分文件。
   - **推送修复**：推到远端新分支，**永不强推**；需要 GitLab 已配置。
   - **合并修复**：推荐「创建合并请求」。也可「直接合并」，但仅在目标分支未受保护、未在本地检出且有改动、可以无冲突合并时可用，否则禁用并写明原因。
   - 「提交并推送」是提交按钮下拉里的显式选项，实际是两次独立命令；提交回执未确认时不会继续推送。
5. **放弃修复**：删除本地修复分支和修复副本；已推送的远端分支不会删除，这一点写在确认框里。
6. **任何写操作回执未知**（提交 / 推送 / 合并 / 创建合并请求）：保留原记录，只提供「核对原操作」，绝不自动重发。与系统现有规则一致。
7. **责任边界**：
   - AI 在审查时只读，在修复时只能写修复副本；
   - 提交、推送、合并只能由用户点击触发；
   - GitLab 凭据只在服务端（设置 → GitLab），界面和 AI 都拿不到。

## 三、主要异常

- Git 能力未接入：整页说明，不按错误处理。
- GitLab 未配置：本地浏览仍可用，远端相关功能禁用并引导去设置。
- 项目不受 Git 管理 / 路径不可用。
- 仓库状态：空仓库、分离 HEAD、浅克隆。
- 读取：读取失败、获取远端时认证失败。
- 修复：修复失败、修复无改动、校验失败。
- 提交与推送：提交被 hook 拒绝、推送被拒（远端有新提交，只引导「获取远端更新」）、推送认证失败。
- 合并：保护分支、合并冲突、合并请求已存在。

逐个状态见 `STATES.md`。

## 四、接口要点（详见 API-DESIGN.md）

- **分层**：界面 → 应用服务读口 / 命令 → 内部 MCP（git-mcp、gitlab-mcp）→ 本机仓库 / GitLab。界面不直接调用 MCP 或 git：授权、凭据、回执都在服务端。
- **读口（候选）**：
  - 仓库：`git.repos.list`、`git.repo.read`
  - 提交与差异：`git.commits.list`、`git.commit.read`、`git.commit.files`、`git.diff.read`
  - 分支与合并请求：`git.branches.list`、`gitlab.mergeRequests.list/read`、`gitlab.connection.read`
- **命令（候选，带 requestKey / 回执 / 未知核对）**：
  - 远端：`git.fetch`
  - 审查：`review.start/stop`、`review.finding.update`
  - 修复：`fix.start/stop`、`fix.file.revert`、`fix.discard`
  - 提交、推送与合并：`fix.commit`、`fix.push`、`fix.mergeRequest.create`、`fix.merge`
- **建议复用执行引擎**：审查是只读模板任务；修复是写入范围限定在修复副本的任务。这样尝试记录、节点执行详情、审批和回执规则都能直接沿用。
- **分期**：
  - P0：只读浏览
  - P1：AI 审查
  - P2：修复 + 提交 + 推送 + 合并请求
  - P3：直接合并、流水线状态

## 五、我的设计建议（待你 / codex 确认）

1. **直接合并**：建议只要目标分支在本地处于检出状态就禁用（不论有没有未提交改动），避免本地文件和分支不同步；原型目前只在有未提交改动时禁用。要不要保留「直接合并」，也建议在 P3 再定。
2. **推送被拒**：P2 只提供「获取远端更新后用新分支名推送」，不提供变基或强推。
3. **对比的父提交**：合并提交默认对比父 1（合并进来的改动），可切换。
4. **修复基于最新提交**：审查针对的是历史提交 a1b2c3d，修复在分支最新提交上进行。问题位置可能已移动，修复结果里每个问题要标「位置一致 / 已移动 / 找不到」。
5. **严重度与维度分开**：严重度为 阻断 / 严重 / 一般 / 建议；维度为 缺陷 / 安全 / 性能 / 质量 / 规范 / 测试。两者分开标注。

完整待确认清单见 `API-DESIGN.md` 第 7 节，包括 MCP 工具命名、修复分支命名与存放、测试命令来源、合并请求模板、GitLab 令牌所需权限、大仓库性能上限等。
